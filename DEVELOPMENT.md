# MShell development guide

## Source layout

The Swift package lives in [MShell](MShell). The `CarveApp` executable launches the native macOS interface. `Sources/app` manages the session tree, windows, tabs, preferences, and credential vault. Interface text uses the standard Apple layout: `Sources/app/Resources/en.lproj/Localizable.strings` and `zh-Hant.lproj/Localizable.strings`, keyed by the English source string, with `defaultLocalization: "en"` in `Package.swift`. Add a string to both files when you add `T("…")` in code; `TerminalInputTests` checks that the two catalogs have the same keys. The language choice is stored as the app's `AppleLanguages` preference, the same value as the per-app language in System Settings, and `package-app.sh` declares the shipped languages in `CFBundleLocalizations`. The `terminal` and `LocalPTY` targets handle terminal state and the local login shell. The `ssh`, `network`, and `file-transfer` targets implement remote sessions and SFTP.

The packaging script builds an optimized release app bundle in `build` by default. Debug builds parse and draw terminal output several times slower, so use the packaged app to judge responsiveness. To use a different build cache or destination, pass them as the first and second arguments to `package-app.sh`.

Use [Humanizer-zh](https://github.com/op7418/Humanizer-zh/blob/main/SKILL.md) when editing the Traditional Chinese interface and README. Use the same terms for the same action, and keep the original conditions, format placeholders, and command examples.

## Local data

MShell stores its working files under `~/Library/Application Support/MShell`. The session catalog stores connection settings and key-file paths. Host fingerprints, saved sign-ins (`saved-sign-ins.json`), and the optional encrypted password vault have separate data files. Quick commands are stored as plain text in `quick-commands.json`. Keep secrets out of saved commands. For UI checks, pass `--workspace /path/to/test-workspace` to the app executable to isolate these files from your regular workspace.

The layout menu in the toolbar and the `mshell layout` command both set the `layout.json` preference. The menu applies the layout at once; a CLI change applies to the next app process. `layout set` accepts `xshell` and `mobaxterm` as aliases for the stored `terminal` and `transfer` values. Pass `--workspace PATH` at the end of a layout command to target an isolated workspace. The Xshell-style and MobaXterm-style chrome lives in `ClassicLayouts.swift`, and its model support (address bar, compose bar, folder following, host monitoring) lives in `ClassicWorkspace.swift`.

Each item in `sessions.json` may carry an `order` once the user drags items into place. `SessionTreeStore.children(of:)` lists ordered items first, then unordered ones folders first and by name, so older catalogs keep their order. `drop(_:on:_:)` applies a drag and renumbers that folder by the custom order even while the tree is sorted by name. The catalog's optional `sorting` field (`nameAscending` or `nameDescending`; absent means custom) picks how `children(of:)` lists items. File transfers go through `TransferQueue`, which `WorkspaceModel.transfers` shares between the file sidebar (`RemoteFileSidebar`, which shows `LocalTreeState` for the local terminal), the two-pane `FileTransferView`, and every layout. The Mac layout shows `FileTransferView` in the main window when `workspaceMode` is `.files`, following the selected tab. The Xshell and MobaXterm layouts show it in `FileTransferWindow` with a server menu. It runs one item at a time on the tab's SFTP channel. Uploads write a temporary `.name.mshell-….partial` file and rename it into place. Downloads write a hidden partial file beside the destination. `SFTPTransfer` keeps 16 reads or writes of 32 KiB in flight and stops at task cancellation. Saved forwarding rules are stored with the connection in `sessions.json`. Local and dynamic forwards listen on this Mac's loopback interface. Reverse forwards ask the server to listen on its loopback interface. Enter a fixed listening port or leave it blank for an automatically assigned port.

The vault keeps its Touch ID unlock material in memory with Secure Enclave protection. A new app process requires the master password. MShell's Secure Enclave SSH key lives in the storage folder as `ssh-key-secure-enclave` (see `AppSSHKey`). It holds a sealed representation that only this Mac can use. New keys sign without Touch ID. Older keys that require it ask once per launch while the key loads, before the SSH handshake, so signing on the connection's event loop never waits for the user. Where passwords that sign in go depends on whether a vault exists. Without one, passwords and key passphrases that sign in are saved by `CredentialVault.rememberWorking` to `DeviceSecrets`: AES-GCM entries, with the entry ID as associated data, under a key rebuilt from a Secure Enclave key agreement that needs no Touch ID. They work after a restart without the master password. Passphrases use the entry ID `passphrase:<key path>`. Without a Secure Enclave, secrets go to the master-password vault as before. `DeviceSecrets` stays on after the vault is created, so a locked vault does not stop sessions from connecting. While the vault is unlocked, `connect` skips the per-session `confirmsEachConnection` check; while it is locked, that check runs. When only the locked vault holds a needed secret (`CredentialVault.lockedVaultIDs`) and Touch ID is set up for this launch, `readWithTouchID` reads those entries into `sessionPasswords` without unlocking the vault, and that prompt stands in for the per-session check. Tests replace the prompt with `enableTouchIDForTesting`. New sessions start with that check on. **Add to vault** (`CredentialVault.addToVault`) saves a password before it signs in. `SavedSignInsView` lists both places (`CredentialVault.Place`), and reveals, copies, or deletes one copy after `WorkspaceModel.authorizeSavedSignIns`. Removing a key calls `forgetRemembered`, which deletes the copy on this Mac and, while unlocked, the vault copy. A session with `confirmsEachConnection` calls `WorkspaceModel.confirmOwner` (Touch ID or the Mac password) before it uses a saved secret.

## Tests

Run `swift test --package-path MShell` from the repository root. SSH and forwarding integration tests use loopback fixtures. SFTP tests also use macOS's `sftp-server`. The test suite exercises separate host-key approvals for the destination and jump host, transfer round trips, reconnect after transport loss, and independent local terminals.

Optional format compatibility tests read from the directory specified by `XSHELL_DIR`. The original Xshell installation and fixtures are external test inputs.

For SSH interoperability checks, set `MSHELL_REMOTE_HOSTS` to a comma-separated list of `user@host[:port]` targets and `MSHELL_REMOTE_KEYS` to a folder with test private keys and a `known_hosts` file containing the verified server keys. Run `swift test --package-path MShell --filter RemoteHostTests`. The second target is also tested through the first as a jump host. Set `MSHELL_REMOTE_LOGIN_ONLY` to a comma-separated list of hosts whose restricted shells can only be checked for successful login.

## Third-party notices

SwiftPM resolves dependencies using [Package.resolved](MShell/Package.resolved). Bundled Visual Studio Code theme color data is distributed with its [MIT notice](MShell/Sources/app/Resources/vscode-themes-license.txt). Workbench colors from MIT-licensed Marketplace themes are distributed with their [license notices](MShell/Sources/app/Resources/vscode-community-themes-licenses.txt). To change the bundled themes, edit the selection in [build-vscode-themes.py](MShell/scripts/build-vscode-themes.py) and run it with a local Visual Studio Code app and the downloaded `.vsix` packages. Linux distribution palettes are defined in `ThemeGallery.swift`; [THEME-INVENTORY.md](THEME-INVENTORY.md) records their sources. MShell's workspace layout and theme picker are native implementations. Xshell session import supports selected fields from compatible profiles. The MobaXterm reader (`MobaXtermImport` in `SessionImports.swift`) follows the field positions of MobaXterm's session export, which Mobatek does not document; it reads SSH (type 0) and SFTP (type 7) sessions and tolerates short field lists from older versions. Import files are decoded as UTF-16 or UTF-8 when marked or valid, then as Big5 (CP950), GB 18030, and Windows-1252. `SessionExport` writes `.mshellsessions` JSON (`SessionsFile`) and CSV; both leave out passwords and rewrite paths under the home folder as `~/…`.
